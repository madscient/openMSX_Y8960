### 3.2 設計方針は「XML で分割」

既存実装は、ブロックごとに別の `MSXDevice` を作り XML で組む方式である。
ブロック間の結線は **id 参照**で行う。

- `RomY8960` の `<opll0>Y8960 OPLL 0</opll0>` → `findDevice()` で解決し、
  7FF4h/7FF2h への書き込みを OPLL デバイスへ中継する
- `Y8960Mixer` の `<channel num="0" idref="Y8960 OPLL 0"/>` → 各チャンネルの
  ゲインを対象デバイスに適用する

**当初計画の「単一 `Y8960` デバイスにする」案は撤回する**（§7）。
既存の `PSG` / `SNPSG` / `Rom8kBBlocks` / `SCC` をそのまま再利用でき、
openMSX の作法にも合っているため、分割方式のほうが良い。

**前提**: id 参照による結線が、追加する OPL2EX にもそのまま使えること。
`Y8960Mixer` の `ChannelCount = 10` に OPL2 用の枠 (num=2,3) と
ADPCM 用の枠 (num=8) が既に確保されているので、成立する見込み（**未検証**）。

### 3.2.1 I/O 割り当て（実測）

`-ext HRA_Y8960` を C-BIOS MSX2+ に挿して `iomap` を取った結果（**確認済み**）。

```
port 3E:      O Y8960 DCSG 0
port 3F:      O Y8960 DCSG 1
port 7A-7B:   O Y8960 OPLL 1
port 7C-7D:   O C-BIOS MSX-MUSIC, Y8960 OPLL 0
port A0-A3: I   PSG
port A0-A3:   O PSG, Y8960 SSGS
port B0-B3: I/O y8960-timer
port B6-B7: I/O y8960-mixer
port C0-C1: I/O Y8960 OPL2 0
port C2-C3: I/O Y8960 OPL2 1
```

- 7Ch が本体 MSX-MUSIC と重なって見えるが、**問題にならない**。
  OPLL にはリードアクセスが無いので、衝突しても両方から音が出るだけである。
  さらに I/O enabler の実装後（§3.3）はリセット直後 7Ch が閉じているので、
  ソフトが明示的に開くまで重ならない。
  切り分けたいときは、本体側の MSX-MUSIC を外した機種でテストするのが早い
- A0-A3 の重なりも**設計どおり**。SSGS は 1 デバイスで、系統は
  レジスタポインタの bit5 で振り分けられる（§3.6）。
  **読み出しは本体 PSG だけ**で、カートリッジ版の SSGS はライトオンリーである

### 3.3 I/O enabler — OPLL 分だけ実装済み

buppu3 の実装には I/O 有効化ラッチが入っていなかった。
**2026-09-09 に OPLL 分（7FF6h）だけを実装した。**

| 7FF6h のビット | 開くポート | デバイス |
|---|---|---|
| b0 | 7Ch-7Dh | `Y8960 OPLL 0` |
| b1 | 7Ah-7Bh | `Y8960 OPLL 1` |

**リセット直後は両方とも閉じている。** これは FM-PAC の動作
（`MSXFmPac.cc` の `reset()` で `enable = 0`、`writeIO` は `enable & 1` の
ときだけ通す）に合わせたもので、マニュアル §3.1 の
「起動直後・リセット直後は無効」とも一致する。
**RTL は 7Ah 側をリセット時に有効にしているが、これは取り違えとして採らない**
（`hardware-notes.md` §6.1、2026-09-09 のユーザー判断）。

**メモリマップド I/O（7FF4h/7FF5h と 7FF2h/7FF3h のトンネル）は
enabler の影響を受けない。** そうでないと I/O を開く手段が無くなる。
実装上は `Y8960OPLL::writeIO()`（直接 I/O、ゲートあり）と
`Y8960OPLL::writePort()`（トンネル、ゲート無し）に分けてある。

ポートの登録自体は XML のまま静的に行い、`writeIO()` の中で弾いている。
OPLL はリードアクセスが無いので、書き込みを落とせば挙動は実機と等価になる。
`iomap` の表示上はポートが埋まって見えるが、実害は無い。

回帰テストは `doc/fork/y8960/tests/opll-enabler.tcl`。

### 3.3.1 7FFFh（I/O Enabler2）【全ビット実装済み 2026-09-09】

| 7FFFh のビット | 開くポート | デバイス |
|---|---|---|
| b0 | C0h-C1h | `Y8960 OPL2 0` |
| b1 | C2h-C3h | `Y8960 OPL2 1` |
| b2 | 3Eh | `Y8960 DCSG 0` |
| b3 | 3Fh | `Y8960 DCSG 1` |
| b4 | A0h-A2h | `Y8960 SSGS` |
| b7 | B0h-B3h | `y8960-timer` |

OPLL (7FF6h) と違い、**こちらはビットの割り当てが RTL と一致している**
（b0 が 1 番目の回路 = C0h 側）。リセット直後は全ビットが閉じており、
これも RTL と一致する（**確認済み**: `y8960_address_decode.v:209-210, 223-224`
および同ファイルのリセット時有効表、`hardware-notes.md` §2）。

OPL2 と MSX-TIMER はリードアクセスがあるので、`writeIO()` だけでなく
`readIO()` / `peekIO()` も閉じているときは 0xFF を返す。
OPLL・DCSG・カートリッジ版 SSGS はライトオンリーなので `writeIO()` だけを弾く。

**MSX-TIMER のカウンタと割り込みは、閉じている間も動き続ける。**
実機の enabler が止めるのはアドレスデコードだけであり、
ブロックそのものを停めるわけではないため。

### 3.3.2 メモリマップド I/O のトンネル【全ブロック実装済み 2026-09-09】

`RomY8960::writeMem()` が窓の書き込みを各ブロックへ渡す。
**enabler の影響を受けない**のは §3.3 と同じ理由による。

**窓の中では 1 番目の回路が高位側に座る**（**確認済み**: 2026-09-09 に
hra1129 さんから直接の回答）。

| アドレス | 渡す先 |
|---|---|
| 7FEAh / 7FEBh | `Y8960 SSGS`（レジスタ番号 / 値） |
| 7FECh / 7FEDh | `Y8960 OPL2 1`（アドレス / データ） |
| 7FEEh / 7FEFh | `Y8960 OPL2 0` |
| 7FF0h | `Y8960 DCSG 1` |
| 7FF1h | `Y8960 DCSG 0` |
| 7FF2h / 7FF3h | `Y8960 OPLL 1` |
| 7FF4h / 7FF5h | `Y8960 OPLL 0` |

**DCSG だけは、アドレス bit0 がアドレス/データの別ではなく回路を選ぶ。**
1 バイト書き込みのレジスタラッチ方式で、レジスタ番号を別ポートに持たないため。

**直接 I/O とは並び方が違う。** 直接 I/O 側で 1 番目が低位に座るのは
OPL2 (C0h) と DCSG (3Eh)、高位に座るのは OPLL (7Ch)。
窓の中は 3 つとも高位が 1 番目である。

| ブロック | 直接 I/O の 1 番目 | 窓の 1 番目 |
|---|---|---|
| OPLL | 7Ch-7Dh（高位） | 7FF4h-7FF5h（高位） |
| OPL2 | C0h-C1h（低位） | 7FEEh-7FEFh（高位） |
| DCSG | 3Eh（低位） | 7FF1h（高位） |

**前提**: この並びは**過去の実装との互換のため**であって、規則から導いたもの
ではない（hra1129 さん）。したがって片方から他方を推論してはならない。

**未実装: 窓は `rammode` が 0 のときだけ開くこと。** RTL は
`memory_io_en = ~rammode` でトンネルごと消す（**確認済み(読解)**:
`hardware-notes.md` §3）が、こちらは `ramEnabled` に関係なく通している。
Phase 1 以前からの積み残しで、今回の 2 ブロックで新たに増えたものではない。
やり直しの値段は `writeMem()` の分岐 1 つと、`getWriteCacheLine()` の見直し。

### 3.4 OPL2EX の作り方【実装済み 2026-09-09】

OPL2EX = YM3812 + ADPCM-B。openMSX の `Y8950` は OPL(OPL1) + ADPCM-B で、
**レジスタ配置・タイマー・ステータス・IRQ がそのまま使える**。
差分は OPL2 の波形選択だけなので、`Y8950` をフォークして
`src/sound/Y8960OPL2.{cc,hh}` を作った。

**落としたもの**: キーボードコネクタ、13bit DAC、`Y8950Periphery`、
およびそれらを駆動するレジスタ（05h, 06h, 0Dh, 0Eh, 15h-17h, 18h, 19h, 1Ah、
07h の b3）。Y8960 のレジスタ表はこれらを全部「廃止」としており、
対応するハードウェアも無い（**確認済み**: `doc/spec` の `OPL2+ADPCM` シート）。

**波形選択**: `sinTable`（dB スケール、正値 [0,DB_MUTE)、
負値 [2*DB_MUTE,3*DB_MUTE) の表現）から 4 面のテーブルを作り、
`Slot` に `wave`（選択値）と `waveTable`（実際に使う面へのポインタ）を持たせた。
無音は DB_MUTE-1 で表す。E0h-F5h がスロットごとに選び、
TEST レジスタ 01h の b5 が全体のゲートになる（クリアなら全スロットが素のサイン）。
リズム用スロットは `Y8950` と同様にサインを直接使う。

**ADPCM は共有した。** `Y8950Adpcm` が `Y8950` に求めるのは
`setStatus` / `resetStatus` / `peekRawStatus` の 3 つとステータスビットだけだったので、
これを `Y8950Status` インターフェースとして `Y8950Adpcm.hh` に切り出し、
`Y8950` と `Y8960OPL2` の双方が実装する形にした。
570 行の ADPCM 実装を二重に持たずに済んでいる。

**代案として YMF262 を OPL2 モードで使う案は却下**（§7）。
**ADPCM も丸ごとフォークする案も却下**（§7）。

### 3.5 OPLLEX は既存実装を使う（作らない）

`YM2413NukeYKTBanked` が既にある。設計を確認した（**確認済み**）:

- `YM2413Core` インターフェースは**変更していない**。`peekRegs()` は
  `std::span<const uint8_t, 64>` のまま
- 4 バンク分の音色を 1 本の配列 `patches[1 + 15*4]` に畳み、
  `inst[ch]` 側でバンクを織り込んで選ぶ
- `<ym2413-core>NukeYKT-Banked</ym2413-core>` で選択する

当初計画では `YM2413Okazaki` をフォークして 4 面の音色テーブルを持たせ、
`YM2413Core` を継承しない独立型にするつもりだった。既存実装のほうが
インターフェースを壊さず、既存の 4 コアと同列に並ぶので優れている。
**当初案は撤回**（§7）。

### 3.6 SSGS【実装済み 2026-09-09】

`src/sound/Y8960SSGS.{cc,hh}` と `src/sound/Y8960SsgCore.{cc,hh}`。
レジスタ配置は `hardware-notes.md` の SSG 節にある。

**1 つのステレオ `SoundDevice`（6 チャンネル）にした。**
パンポットがチャンネルごとなのに対し、openMSX の `MSXMixer` は
**デバイス単位の balance しか持たない**（**確認済み**: `MSXMixer.hh` の
`ChannelSettings` は `record` と `mute` だけ）。したがって `PSG` を 2 個並べて
ミキサー設定を動かす方式では 6ch 独立パンポットを表現できない。

`Y8960SsgCore` は `AY8910` のフォークで、`SoundDevice` ではない。
落としたのは periphery（YMZ 系に I/O ポートは無いのでレジスタ 14/15 も無い）、
Debuggable（`Y8960SSGS` が $00-$3F 全体で持つ）、`type` による AY/YM 判定
（YM2149 固定）。vibrato/detune の設定は残してある。

パンポットの分配則はデータシートに無いため、EPSGemuEngine と同じく
YMZ280B の則を採った。またコアの出力が片極性なので、**パン適用前に
無音時レベルを差し引いている**。省くと直流が定位に漏れる。

回帰テストは `tests/ssgs-panpot.tcl`。

**リセット直後は閉じている**（2026-09-09 に hra1129 さんが方針を確定）。
カートリッジ版は音源の I/O ポートをリセット時に閉じておく。
RTL の `ff_ssg_io_en = 1` は WIP のプレースホルダなので採らない。

**カートリッジ版の SSGS はライトオンリー。** A0h-A2h は本体 PSG と重なっており、
リードに応じると `MSXMultiIODevice` が両者の AND を取って本体 PSG の読み出しが
壊れる。回帰テストは `tests/ssgs-write-only.tcl`。

### 3.6.1 カートリッジ版と本体内蔵版

Y8960 には **MSX 本体に内蔵して既存デバイスを置き換える**構成がある。
**2026-09-09 に、両者の違いが 4 点で確定した**（**確認済み**: hra1129 さんの回答）。

| | カートリッジ版 | 本体内蔵版 |
|---|---|---|
| I/O イネーブラー | **有**（リセット時は閉） | **無**（常時開） |
| メモリマップド I/O のトンネル | **有** | **無** |
| SSGS の GPIO | **無し** | **有り** |
| SSGS のリード | ライトオンリー | **リード/ライト両対応** |

本体内蔵版そのものはまだ作っていないが、**分岐は 4 つと分かっている**ので
器を先に置く。XML の要素で選ぶ。

| 要素 | 既定 | 持つデバイス | 状態 |
|---|---|---|---|
| `<use_io_enabler>` | `true` | `Y8960-OPLL` / `Y8960-OPL2` / `Y8960-SSGS` / `Y8960-DCSG` / `MSX-TIMER` | 実装済み |
| `<use_mmio_tunnel>` | `true` | マッパー種別 `Y8960`（`RomY8960`） | 実装済み |
| `<readable>` | `false` | `Y8960-SSGS` | 実装済み |
| `<gpio>` | `false` | `Y8960-SSGS` | 実装済み（§3.6.2） |

`<use_mmio_tunnel>` が `false` のとき落ちるのは、**7FE0h-7FFFh の窓ごと**である。
トンネルだけでなく I/O Enabler1/2 のレジスタも消える。本体内蔵版には
開閉するものが無いので、窓に残す意味が無い。
マッパーとバンクレジスタ・SCC・RAM enable は影響を受けない。

**要素名は暫定**。本体内蔵版の構成を実際に書く段で見直してよい。

**落とし穴: `<readable>` だけでは SSGS のリードは通らない。**
カートリッジ版の XML は SSGS のポートを `<io base="0xA0" num="4" type="O"/>`
と書いており、**openMSX が入力側にデバイスを登録しない**。
`readIO()` が呼ばれないので `<readable>true</readable>` は効かない。
本体内蔵版の構成では `type` を落として I/O 両方にする必要がある
（**確認済み**: `type="O"` のまま `readable` を立てた構成を走らせ、
リードが SSGS に届かないことを見た）。

### 3.6.2 SSGS の GPIO【実装済み 2026-09-09】

本体内蔵版の SSGS は **GPIO を持つ**。カートリッジ版には無い。

**確定した仕様**（**確認済み**: 2026-09-09 に hra1129 さんから直接の回答）。

- **プライマリ側の 1 系統だけ**が持つ。セカンダリには無い
- **本体 PSG の代替**なので、繋がるものも本体 PSG と同じ。
  すなわちジョイスティック 2 ポート、かなランプ、カセットのモータ制御

実装は `AY8910` から落としてあったものを戻す形になった（§3.6）。

| 場所 | 足したもの |
|---|---|
| `Y8960SsgCore` | `AY8910Periphery*`。`nullptr` の系統ではレジスタ `$0E`/`$0F` は素の記憶域のまま |
| `Y8960SSGS` | プライマリの `$0E`/`$0F` だけをコアに通す。無効なら 0xFF |
| `Y8960SSGSDevice` | `AY8910Periphery` を実装。中身は `MSXPSG` と同じ結線 |

`AY8910` の `ignorePortDirections`（ポート A を強制的に入力にする）も
一緒に戻してある。本体 PSG 向けに書かれたソフトがそのまま走る側なので、
`MSXPSG` と挙動を揃える必要がある。

**残っている非対称**。`Y8960SsgCore` はレジスタ `$0E`/`$0F` を
（periphery が無くても）記憶域として持っている。カートリッジ版では
`Y8960SSGS` が手前で弾くので外からは見えないが、実チップに
「そこに何があるか」は分かっていない。**未確認**。

### 3.8 マッパーと RTL の突き合わせ【2026-09-09】

`RomY8960` は upstream の `RomKonamiSCC` ではなく buppu3 実装で、
互換モードが Konami SCC 相当、そこに RAM モードが足してある。
2026-09-09 に**一次情報の RTL を実際に読んで**突き合わせた
（`hardware-notes.md` §4.1 に読解結果）。

**一致していたもの**（変更不要）。

| 項目 | |
|---|---|
| バンクレジスタのアドレス | 互換 5000/7000/9000/B000、RAM 4?FB / 4?FC-FF |
| モードによるレジスタの排他 | 互換側は `rammode=0` のときだけ、RAM 側は `rammode=1` のときだけ受け付ける |
| リセット値 | `rammode=0`、バンク 0/1/2/3 |
| ミラー | A14/A13 だけでデコードするので 0000-3FFF と C000-FFFF にも同じバンクが出る |
| SCC 音源レジスタ 9800-9FFFh | `bankreg2` が 3Fh。実装の `(value & 0x3F) == 0x3F` は 6bit しか保持しない RTL と等価 |

**食い違っていたもの**（いずれも buppu3 実装から引き継いだまま。**未実装**）。

| # | RTL | `RomY8960` |
|---|---|---|
| 1 | RAM モードで SCC 音源レジスタが 7800-7FFFh にも出る（`bankreg1` が 3Fh） | 9800-9FFFh だけ |
| 2 | メモリのアドレスは `bankreg[4:0]` の 5bit だけで決まる（8KB × 32 = 256KB） | バンク番号を 16 で剰余し、16-31 を別の RAM オブジェクトに割り当てる |
| 3 | ROM/RAM のバンクによる区別が無い。RAM モードなら 32 バンク全部が書ける | バンク 16 以上でしか書けない |
| 4 | 4000-5FFFh の書き込み保護が無い | 6000h 未満は書けない |
| 5 | `rammode` はアドレスに寄与しない。書き込み可否と窓の有無だけを決める | ROM/RAM を別オブジェクトに分けている |
| 6 | `rammode=1` でメモリマップド I/O の窓が消える | 消えない（§3.3.2 に既出） |

**直す前に確認が要る。** RTL の 3 つのコメントと manual が、
それぞれ違う ROM/RAM 境界を書いており、**どれもコードと一致しない**

### 3.8.1 バンクメモリと MMIO 窓【実装済み 2026-09-10】

§3.8 の食い違い #1・#6 に決着を付けるための設計。**RTL の読解ではなく
こちら側の判断を含む**ので、行ごとに出所を書く。

#### 決めた 4 つの規則

| | 規則 | 出所 |
|---|---|---|
| 1 | SCC 音源レジスタは、その region 自身のバンクレジスタが 3Fh のとき、その region の 1800-1FFF に出る。**RAM モードのバンク0 だけは出さない** | RTL のゲート規則の一般化（判断） |
| 2 | MMIO 窓は、**バンク1 が ROM を出しているときだけ**出る | RTL の `~rammode` の置き換え（判断） |
| 3 | RAM モードのバンク0 は書き込み不可。書き込みは 48FB / 48FC-48FF にだけ行く。読み出しは `bankreg0` が選んだ 8KB がそのまま見える | 現行実装の踏襲 |
| 4 | バンク 3Fh を RAM バンクとして扱わない | バグ修正（後述） |

規則 1 の結果、SCC の窓は 4 つの region すべてに出せる。
5800-5FFF / 7800-7FFF / 9800-9FFF / B800-BFFF。
このうち 9800-9FFF だけが Konami SCC 互換で、残る 3 つは拡張。
RTL に在るのは 9800-9FFF と 7800-7FFF の 2 つで、後者は RAM モード限定。
その限定を外し、残る 2 region に広げたのがこの規則。

規則 2 を条件式にすると `!(ramEnabled && isRamRegion(3)) && bankreg1 != 3Fh`。
**`rammode` を直接見ない。** RAM モードでも `bankreg1` が ROM バンクなら窓は出る。

#### なぜこの形か

MMIO 窓 7FE0-7FFF は SCC 窓 7800-7FFF に**完全に含まれる**。だから両者の衝突は
部分的にならず、「バンク1 が SCC なら MMIO は全部無い」の 2 状態しか生じない。
優先順位や読み書きの非対称を持ち込まずに、デコードが 1 本の条件式で書ける。

**前提**: MMIO 窓のアドレスが 7FE0-7FFF から動かないこと。動けば包含関係が
崩れ、規則 2 は書き直しになる。

#### RTL との差（意図的）

RTL は `memory_io_en = ~rammode` で、RAM モードなら無条件に窓が消える。
規則 2 はバンク1 の内容で決めるので、**RAM モードでも窓が残る構成がある**。
これを許容と決めた。

利点が 1 つある。I/O イネーブラ (7FF6h / 7FFFh) は MMIO 窓にしか入口が無く、
直接 I/O ポートを持たない。RTL の規則だと RAM モード中はイネーブラを変更できず、
一度 ROM モードに戻る必要がある。規則 2 なら、バンク1 に ROM バンクを置いて
いる限り RAM モード中でも変更できる。

RTL 側を直すかどうかは hra1129 さんの領分。

#### 規則 4 — 既存の範囲外アクセス

`isRamRegion` は「バンク番号 >= 16」で RAM と判定する。**バンク 3Fh もこれを
通る。** その先の `getRamAddress` は `bank - 16 = 47` を返すが、`ram` は
16 バンク (128KB) しかない。`assert` はあるが release ビルドでは範囲外アクセスに
なり、`getReadCacheLine` は生ポインタを CPU 側に渡すのでそちらの方が悪い。

再現条件は「RAM モード + どこかの region にバンク 3Fh + その region を読む」。
今は region 4 でしか起きないが、規則 1 で 4 つの region すべてが該当するようになる。

**確度**: 確認済み(読解)。`isRamRegion` / `getRamAddress` と読み出し 3 経路の
分岐を読んだ。**未検証** — 実際に走らせて踏んではいない。

ROM 経路は安全側に倒れる。`RomBlocks::setRom` が範囲外ブロックを
`unmappedRead` に落とす（**確認済み(読解)**）。危ないのは RAM 読み出し経路だけ。

**残る未決**: バンク 3Fh を置いた region の、SCC 窓に当たらない部分 (0000-17FF) に
何が見えるか。openMSX の現行モデルでは ROM のブロックマスクが効いて ROM バンク 15、
RTL のモデル (`bankreg[4:0]`) ではバンク 1Fh になる。§3.8 の #2 が決まるまで保留。

#### やり直しの値段

`sccEnabled` の bool 1 個を region ごとの判定に置き換えるのが本体。
`peekMem` / `readMem` / `getReadCacheLine` / `writeMem` / `getWriteCacheLine` の
各経路と `invalidateDeviceRWCache` の呼び出しが region 単位になる。
変更は `src/memory/RomY8960.cc` 1 本に収まるが行数は出る。

セーブステートに `sccEnabled` が入っていたので、版を 2 に上げ、版 1 の
セーブステートでは値を読み捨てる。`bankReg` から導出できるので情報は足りている。

#### 検証（**確認済み** 2026-09-10）

`tests/mapper-windows.tcl` が 13 件。窓が出ているかどうかは、窓に書いた値が
届いた先（SCC の波形メモリ、OPLL のレジスタ）で見る。

**判別力を確かめてある。** 修正前のコードに戻して同じテストを走らせ、
**6 件が落ちることを確認した**。落ちたのは region 2/3/5 の SCC 窓、
バンク1 の SCC/RAM が MMIO を隠すこと、消えた書き込みが SCC に落ちること、
region 3 の RAM バンク判定。

判別力が無い項目が 2 つあり、どちらも将来の回帰を捕まえるための番人である。

- 「RAM モードのバンク0 に SCC が出ない」— 修正前はそもそもバンク0 に窓が
  無いので、修正前でも通る
- 「バンク 0x3F が RAM として読まれない」— Release ビルドには assert が無く、
  範囲外を読んでも値が返るだけなので、修正前でも通る。Developer ビルドで
  走らせれば判別力が出るが、3rdparty を Developer で作り直す必要がある

**Tcl の `reset` はスクリプト実行中には効かない**（**確認済み**: RAM モードで
`reset` した直後に互換モードのバンクレジスタを叩いても無視された）。
リアクタが後で処理する。テストは状態をレジスタで書き戻している。

### 3.7 デジタルミキサーと出力の切り替え【実装済み 2026-09-09】

**2 つの別物が同じデバイスに載っている。片方だけが実在する。**

#### 出力の切り替え（実在する）

**カートリッジは音声を MSX 本体に戻さない**（**確認済み**: hra1129 さんの回答）。
出力は 2 本の別の線で、実機では人が外で切り替えるかミックスする。
`y8960-mixer_output` 設定がそれで、3 値をとる。

| 値 | 鳴るもの |
|---|---|
| `y8960` | Y8960 の音源だけ |
| `msx` | 本体の音だけ |
| `mix` | 両方 |

既定は XML の `<default_output>`。**カートリッジ版は `y8960`、本体内蔵版は
`mix`**（内蔵版に「本体側の出力」が別に在るわけではないため）。

`MSXMixer` 側は buppu3 実装の 2 値（内蔵か外部か）を 3 値に広げた。
`OutputSelect::{INTERNAL, EXTERNAL, BOTH}`。

#### ミキサー本体（器だけ。何も繋がっていない）

音源チップごとの左右ゲインと、全体に掛かる左右ゲインを持つ。
どちらも**ミキサーの入力段**、つまり音源チップ 1 個ぶんの出力に掛かる。

| メソッド | 効果 |
|---|---|
| `Y8960Mixer::setChannelGain(ch, l, r)` | その音源の出力に左右のゲインを掛ける |
| `Y8960Mixer::setMasterGain(l, r)` | Y8960 の音源すべてに左右のゲインを掛ける |

**B6h-B7h はこれらに繋がっていない。** B6h でレジスタ番号、B7h でデータ、
という PSG と同じ形の入口はある（hra1129 さん）。だがレジスタアレイの中身が
未定なので、ポートは値を憶えるだけでゲインは 1.0 のまま動かない。
繋ぐのは `writeIO()` から上の 2 つを呼ぶだけである。

**器が実際に効くことは実測してある**（2026-09-09、§8 の経緯 (14)）。

**ゲインは `MSXMixer::setDeviceGain()` に行き、`updateVolumeParams()` の
最後に掛かる。** デバイス内部のパンとは独立している。

**やってはいけないこと**: `SoundDevice::setBalance()` を使う。
あれは**デバイス内部のチャンネルのパン**であって出力ゲインではない。
buppu3 実装はこれを使っており、SSGS のように自前でパンを持つデバイスでは
定位が壊れる（**確認済み**: 全チャンネルに 1.0/1.0 を掛けると、
左右が混ざって音量が 2.4 倍になった）。この用途の
`MSXMixer::setBalance(name, ...)` と `SoundDevice::setBalance(ch, l, r)` は
削除し、`src/sound/SoundDevice.{cc,hh}` は上流と同一に戻した。

| 窓の中の 1 番目 | **高位側（確定）** | 7FECh が OPL2 0 | `bus_address[1]` | 高位側 |

**DCSG は 3Eh / 3Fh**。2026-09-09 に hra1129 さんから直接の回答があり、
xlsx の 3Eh/3Fh が正、RTL の 7Eh は古いと確定した。**これが最も強い出典**で、
RTL より優先する。
DCSG は 1 ポートずつで、**アドレス bit0 が 2 回路のどちらかを選ぶ**
（**確認済み**: `sn76489_audio_patch/sn76489.v:26-27` の `w_cs0_n` / `w_cs1_n`）。
したがって 3Eh → DCSG 0、3Fh → DCSG 1。

**前提: Y8960 自体が WIP なので、これらは変わりうる。**
そのためアドレスは C++ 側に定数として持たず、`share/extensions/HRA_Y8960.xml` の
`<io base=...>` にのみ書く。変更コストは XML 1 行と本書の表だけに収まる。

**OPLL の対応は buppu3 実装・RTL・xlsx の三者で一致している**（2026-09-09 に
`opll.v:27-28` と `y8960_address_decode.v` を読み直して確認）。
7Ch-7Dh + 7FF4h-7FF5h が 1 番目の回路で、従来の MSX-MUSIC 互換の側である。
以前ここに「RTL とは逆」と書いていたのは誤りだった。

**ミキサーは B6h-B7h に移した（2026-09-09、暫定）。**
buppu3 実装の 40h-41h は現 RTL の system controller (40h-4Fh) と衝突する。
`ioport.txt` は `B6h-B7h: MSX-SOUND MIXER` と書いており、
hra1129 さんも「まだ作ってないので**未確定**。B6h-B7h あたりがいいかも」と
述べている（**確認済み**: Discord のスクリーンショット）。
根拠が 2 つ揃い、据え置いても衝突が残るだけなので移した。

**これは確定ではない。** hra1129 さんが実装したときに変わりうる。
やり直しの値段は `HRA_Y8960.xml` の `<io base>` 1 行と本書の表だけ。

**OPL2 と DCSG のトンネルの向きは、2026-09-09 に xlsx が正と確定した。**
hra1129 さんの回答は「窓の中は高位側から 1 番目→2 番目、直接 I/O は
OPL2 と DCSG では低位側が 1 番目、OPLL は高位側が 1 番目。いずれも過去の実装
との互換のため」（**確認済み**: 本人の回答）。§3.3.2 に表がある。

**訂正**: ここには以前「xlsx が自己矛盾しており、RTL を採って C0h-C1h と
7FECh-7FEDh を同じ回路に繋いだ」と書いていた。**これは誤りだった。**
RTL の `bus_address[1]` から窓の側の対応まで組み立てたが、
窓と直接 I/O は別々の理由で並びが決まっていた。

**OPLL の enable まわりは RTL と xlsx／マニュアルが食い違う**
（`hardware-notes.md` §6.1）。7FF6h の bit0 が 7Ah 側を開き、リセット直後は
7Ch-7Dh が無効・7Ah-7Bh が有効になっている。I/O enabler を実装する段
（§7 の保留事項）で、どちらに従うかを決める必要がある。確認事項。

- **RAM モードで MMIO レジスタをバンク0 に再マップする** — 却下（2026-09-10）。

  必要が無いと分かった。RAM モードのレジスタ (48FB / 48FC-48FF) は最初から

  レジスタが発火する**（`src/sound/SCC.cc`）ため、読み書きの非対称を
  持ち込むと挙動が説明しにくくなる

### 2026-09-09 (9) — MSX-TIMER の割り込みが上がっていなかった

- 「タイマーから割り込みがかかるか」を確かめにいったところ、**上がっていなかった**。
  buppu3 実装から引き継いだままの欠陥で、こちらで持ち込んだものではない
- **原因**: `MSXTimerCore` の `clock` が 2 つの役目を兼ねていた。
  `updateSchedule()` が `clock.reset(time); clock += period;` として
  `clock` を**次の同期点まで進めて**いたため、`checkCounter()` が
  経過クロック数として使う `clock.getTicksTillUp(time)` が、
  同期点に達した瞬間にちょうど 0 になる。カウンタが進まず、
  `ff_count_end` が立たず、`updateIrq()` は何も上げない
- **見えにくかった理由**: フラグの読み出し (B2h) は `peekIrqFlag()` 経由で、
  `checkCounter()` をその場で回して答える。**フラグは正しく立って見える**。
  レジスタに書き込むと `updateCounter()` が走って確定するので、
  そこで初めて割り込みが上がる。つまり「ソフトがレジスタを触ったときだけ
  遅れて割り込みが来る」状態だった
- **修正**: `clock` を「どこまでカウンタに反映したか」だけの役目にした。
  `updateCounter()` の末尾で `clock.advance(time)`（端数は持ち越す）、
  `checkCounter()` は切り上げの `getTicksTillUp` ではなく `getTicksTill` を使い、
  `updateSchedule()` は `clock` を動かさず `setSyncPoint(clock + period)` する。
  `reset()` でも `clock.reset(time)` するようにした（初期値が 0 のままだった）
- 検証（**確認済み**: 実際に走らせた）:
  - `tests/timer-irq.tcl` の 5 項目。**タイマーの線 (`y8960-timer.IRQ`) と
    CPU の線 (`z80.pendingIRQ`) の両方**を見ている。フラグだけでは、
    フラグが立っても線が上がっていない今回の欠陥を捕まえられない
  - **VDP の割り込みを止めてから測っている**（R#1 の b5）。残すと
    `z80.pendingIRQ` がどちらの線か区別できない
  - **判別力**: 修正前のコードでビルドし直して同じテストを回すと、
    手順 3 と 5 が `timer.IRQ=0` になる
  - 他の 6 本すべて非回帰

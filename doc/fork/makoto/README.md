# Makoto（YM2608 カートリッジ）— フォーク版から残す知見

対象読者は開発者。

Makoto は YM2608（OPNA）を 1 個載せた MSX 用のサウンドカートリッジである。
このフォークは 2026-09-22 から独自の実装を別ブランチに持っていたが、upstream が
2026-10-11 に Makoto を取り込んだ（upstream の `f07bee985`）ので、独自の実装は
2026-10-12 にやめた。**今は upstream の実装（`src/sound/YM2608.cc`、
`src/sound/MSXMakoto.cc`、`share/extensions/Makoto.xml`）をそのまま使う。**

本書は、独自の実装を持っていた間に分かったことのうち、実装が変わっても役に立つものを
抜き出した記録である。独自の実装、その試験、元の計画文書はリポジトリの参照からは
外れている。元の計画文書はコミット `49316c073` に入っていて（本書と同じ
ディレクトリの `implementation-plan.md`）、SHA を指定すれば読める。

確度の印は元の計画文書のものを引き継いだ。**確認済み**とあるのは、独自の実装を
動かして確かめた当時の結果で、upstream の実装で確かめ直したものではない。
upstream の実装について書いた箇所は、断りの無いかぎり、ソースを読んだだけで
動かしていない。

## 1. ハードウェアの前提

| | 内容 | 確度 |
|---|---|---|
| I/O | `14h` 表アドレス（W）／ステータス0（R）、`15h` 表データ（W）／データ（R）、`16h` 裏アドレス（W）／ステータス1（R）、`17h` 裏データ（W）／ADPCM データ（R） | 確認済み（vgmplay-msx の `src/drivers/Makoto.asm` の定義を読んだ） |
| クロック | 8MHz | 確認済み（同じファイルの `Makoto_CLOCK`）。実機の水晶が正確に 8.000MHz かは未確認 |
| サンプルメモリ | DRAM、x1 ビット、256KB | upstream の作者が設計者から聞いたと書いている（伝聞） |
| IRQ | `/INT` に直結 | 同上（伝聞） |
| リズム音の波形 | チップに内蔵された ROM | §5 |

プリスケーラと生成レートの関係（8MHz のとき）。プリスケーラはアドレス `2Dh`-`2Fh` への
書き込みで切り替わる。YM2608 のデータシートでは、8MHz で有効なのは 6 だけである
（upstream のレビューでの指摘。伝聞）。

| プリスケーラ | FM + リズム + ADPCM | SSG |
|---|---|---|
| 6（リセット後） | 8MHz÷144 ≈ 55,556Hz | 8MHz÷32 = 250,000Hz |
| 3 | ÷72 ≈ 111,111Hz | ÷16 = 500,000Hz |
| 2 | ÷48 ≈ 166,667Hz | ÷8 = 1,000,000Hz |

## 2. 独自の実装と upstream の実装の違い

独自の実装を前提にした試験やスクリプトを upstream の実装に合わせるときに、変わるもの。

| | 独自の実装 | upstream の実装 |
|---|---|---|
| レジスタのデバッガブル | `Makoto regs`（最後に書いた値） | `Makoto registers`（実効値） |
| サンプルメモリのデバッガブル | `Makoto ADPCM RAM` | 同じ |
| サウンドデバイス | `Makoto`（FM + リズム + ADPCM）と `Makoto SSG` | 同じ名前。FM 側は声部ごとのチャンネルを持つ |
| リズム音 | ROM を `systemroms` から SHA1 で拾う。無ければ鳴らない | データを内蔵している（§5） |
| `16h` / `17h` のデバッガからの読み出し | `FFh` | 副作用なしで実際の値 |
| 既定の音量 | — | 付け直されている。録音のピークや実効値を見る試験は、期待値を取り直す |
| ADPCM-B の EOS / BRDY の IRQ | ステータス1 を読んだときに反映（§3 の 4） | 読み出しを待たずに IRQ 線へ出す |
| ADPCM-B の CPU 転送の境界 | ymfm のまま（§3 の 2・3・5） | 実機の報告に合わせて直してある |
| SSG | ymfm の `ssg_engine` | openMSX の `AY8910`（YM2149 として） |

upstream の実装の名前は、拡張 XML のデバイス `id`（`Makoto`）の後ろに接尾辞を付けて
作られる（**確認済み**: 2026-10-12 に、upstream の `f07bee985` に追従したビルドで
`-machine C-BIOS_MSX2+ -ext Makoto` を走らせた。サウンドデバイスは `Makoto` と
`Makoto SSG`。デバッガブルは `Makoto registers`（512 バイト）、`Makoto ADPCM RAM`
（262144 バイト）、`Makoto SSG regs`（16 バイト）。I/O ポートからレジスタ `30h` に
`5Ah` を書くと、`Makoto registers` の `30h` が `5Ah` になる）。

## 3. ymfm の挙動で、実機と違う点

ymfm のコミット `81aec25ccbb98f4873a255f7551ac4dadac59b4a`（2026-07-27）についての記録。
1〜3 は、ymfm を openMSX に載せて走らせ、挙動を確かめた（**確認済み**、2026-09-22）。
4 と 5 はソースを読んだだけ。実機との突き合わせは、upstream の Makoto の作者による
報告があるものだけ（伝聞。PR #2209 と、その実装に付いていた文書による）。

1. **フラグマスク `110h` のリセット値は `1Ch` で、EOS・BRDY・ZERO がステータス1 に
   出ない。** `110h` を書き換えるまで BRDY は 0 のまま。
   確かめ方: `110h` を書かずに読むと BRDY は 8 回とも 0、`00h` を書くと 8 回とも 1。
   実機の報告は無い。upstream の実装も初期値は `1Ch`
2. **ADPCM-B の記録で、終了アドレスの最後の 1 バイトが書かれない。**
   `adpcm_b_channel::write` は書く前に終端を見て、最後のバイトの位置なら書かずに
   EOS を立てる。x1 ビット DRAM では、終了アドレス `E` に対して `((E+1)<<2)-1` 番地。
   確かめ方: 終了アドレス `0000h` で `A1 A2 A3 A4` を書くと、RAM は `A1 A2 A3 FF`。
   **実機は違う**: Makoto V5 を Sanyo の MSX2+ と Panasonic の turbo R に挿した報告では、
   4 バイトとも書かれた
3. **ADPCM-B の CPU からの読み出しは、limit アドレスの最後のバイトを読む前に 0 番地へ
   戻る。** 確かめ方: limit `0000h` で `B1`-`B8` を書いて読むと
   `B1 B2 B3 B1 B2 B3 B1 B2`。limit（`10Ch`/`10Dh`）を大きくしておけば起きない。
   **実機は違う**: 同じ実機の報告では `B1 B2 B3 B4` を繰り返した
4. **ADPCM-B の EOS と BRDY は、ステータス1 を読んだときにしか IRQ に反映されない。**
   ソースを読んだだけで、**未検証**。タイマー A/B の IRQ は満了した時点で立つ。
   upstream の実装は、読み出しを待たずに IRQ 線へ出すように変えている。
   実機と突き合わせたとは書かれていない
5. **書き込みを終えていない ADPCM-B の CPU 書き込みを、ymfm は覚えていない。**
   実機の報告（Makoto V4）では、終了アドレスまで書かずにモード `00h` を経て
   読み出しモードにすると、ADPCM のリセットまで最後に書いたバイトが返る。
   ymfm は `00h` への書き込みで 2 回のダミー読み出しからやり直し、その後は開始アドレスから
   RAM の中身を返す（ソースを読んだだけで、**未検証**）

ほかに分かっていること。

- どの fidelity でも、ymfm が FM を保持する時間は FM の 1 周期で同じ。fidelity が
  変えるのは SSG の扱いだけ（MIN は SSG 3 サンプルを 2 つに重み付き平均、MAX は
  4 回繰り返し）。`ymfm_opn.h` の注記と、下の一致試験による
- `ym2608` を継承すると、protected の `clock_fm_and_adpcm()`・`m_last_fm`・`m_ssg` を
  直接回せる。`generate()` を通さずに FM と SSG をそれぞれの実レートで取り出せて、
  出力は `generate()` とサンプル単位で一致する（**確認済み**: FM 6 声、SSG 3 声、
  リズム 6 音、ADPCM-B を鳴らすレジスタ列で比べ、不一致 0。レジスタの書き込みを
  3 つ抜いた対照では全部の場合で不一致が出た）
- ADPCM-B の BRDY と EOS、タイマー B の位相は、`generate()`（または上の刻み）を
  回したときにしか進まない

## 4. openMSX に載せるときに分かったこと

- **CPU から見える状態を、音声の生成に載せない。** openMSX は音声の生成と
  エミュレーションを完全には同期させない（`speed` を変えても音程を保つため）。
  ステータスや IRQ の時点が音声の生成で進む作りにすると、`speed` の変更、ポーズ、
  リバースをまたいだときに、同じ時刻でも CPU から見える値が変わる。upstream の実装は
  この不具合を出して、音声の経路とエミュレーションの経路を分けて直した（伝聞。
  独自の実装も同じ作りだったが、不具合が出るかは確かめていない）
- **チャンネルが 1 つのサウンドデバイスには、0 で初期化されていないバッファが渡る。**
  サンプルは加算でなく代入する（`SoundDevice::mixChannels()` のコメント）。
  加算すると出力が発散する
- **モノラルのデバイスは、中央で左右に 1/√2 ずつ出る。** ステレオから分けると 3dB 下がる
- **上の 2 つは `record_channels` の録音では見えない。** 録音するチャンネルは 0 で
  初期化された別のバッファを通るため。音量や定位を見る試験は、全体の出力
  （`record -audioonly`）を録る
- **Unix 系のビルドは、ソースを `*.cc` のワイルドカードで集める。** `.cpp` のまま
  置いたファイルは黙って落ちる（`build/main.mk`）
- **サンプルメモリは `Ram` で持つ。** `std::array` だと、XML のセーブステートでは
  1 要素ずつの項目になり、リバースのスナップショットでは差分圧縮が効かない
  （`serialize_core.hh` と `serialize.hh` を読んだ見立てで、**未計測**）

## 5. リズム音のデータ

YM2608 のリズム 6 音はチップに内蔵された ROM に入っている。独自の実装が拾っていた
ROM ファイルは 8192 バイトで、SHA1 は `50b6c3e288eaa12ad275d4f323267bb72b0445df`。
これは libvgm の再構成データ（MAME の fmopn 由来、GPL-2.0-or-later の表示）と同一である
（**確認済み**: 2026-09-29 に SHA1 が一致した）。upstream のソースの注記は、
チップの ROM は読み出せず、このデータはチップの出力から再構成して実物の YM2608 と
突き合わせたものだとしている（伝聞）。

独自の実装は、このデータを同梱しなかった（2026-09-29、ユーザー判断）。理由は、
チップ内蔵のデータを再配布してよいという根拠が確かめられなかったこと。
**upstream の実装はこのデータをソースに内蔵している**（`src/sound/YM2608AdpcmRom.hh`）。
upstream に追従した時点で、このフォークのソースとバイナリにも入る。

内蔵されたデータについて、2026-10-12 に確かめたこと（**確認済み**）。

- MAME はこのデータを内蔵せず、ROM イメージ `ym2608_adpcm_rom.bin` として読み込む。
  ハッシュ（CRC32 `23c9e0d8` と上の SHA1）は内蔵されたデータと同じ
  （MAME の `src/devices/sound/ymopn.cpp` を読んだ）。同じ箇所に、出力の解析で
  吸い出したもので decap ではない、という注記がある
- decap した YM2608B から読んだ ROM と、実質的に一致する。nukeykt/YM2608-LLE の
  `fmopna_rom.h` にある `rss_rom`（8192 バイト）は、1 バイトの上下 4 ビットの並びが逆。
  入れ替えて比べると 8188 バイトが同一で、違う 4 バイトは 6 音のうち 4 音の最後の
  1 バイト（`043Fh`、`1B7Fh`、`1CFFh`、`1F7Fh`）

内蔵して配ってよいのかを upstream に尋ねた
（https://github.com/openMSX/openMSX/issues/2238 、2026-10-12、ユーザーの承認を得て投稿）。
返事はまだ無い。

## 6. 生成レートごとの CPU 負荷

独自の実装での実測（**確認済み**）。条件は、C-BIOS_MSX2+、`renderer none`、
`throttle off`、`sound_driver sdl`、起動後 10 秒から 120 秒ぶんを計時、各 5 回を交互に
実行した平均。「演奏中」は FM 6 声と SSG 3 声を鳴らしっぱなし。数字は拡張なしからの
増分。2 つの表は別のマシンなので、互いには比べない。

1 本のストリームで fidelity を変えた場合（2026-09-30、拡張なしは 858ms）。

| | 無音 | 演奏中 |
|---|---|---|
| MIN（約 167kHz） | 3112ms | 4688ms |
| MED（約 333kHz） | 4026ms | 5335ms |
| MAX（1MHz） | 6943ms | 8764ms |

FM と SSG を実レートの 2 本に分けた場合（2026-09-30、別のマシン）。

| | 無音 | 演奏中 |
|---|---|---|
| MIN（2 回） | 1896 / 1963ms | 2831 / 2881ms |
| MAX | 3763ms | 4808ms |
| 実レート（2 回） | 1961 / 1842ms | 2966 / 2931ms |
| 実レート + 無音のバッファを飛ばす | 1394ms | 2784ms |

- 無音の MAX は MIN の約 2.2 倍。実レートは MIN と誤差の範囲で、MAX の約半分
- 増分には生成とリサンプルの両方が入っている。分けて測ってはいない
- upstream の実装は実レートの 2 本で、無音の声部を飛ばす。そちらの負荷は測っていない

## 8. 配布

独自の実装のビルドを `21.0-makoto.1`（取り下げ）と `21.0-makoto.2` として
GitHub Releases に出していた。2026-10-12 に、リリース、タグ、ブランチを消した。
Makoto だけを載せた版は、今後このフォークからは出さない（ユーザー判断）。
Makoto 入りのビルドが要るときは、`main` のリリースを使う。次のリリースの時期は
`doc/fork/release/README.md` の §1 にある。

配布で決めていたことのうち、ほかのライブラリを足すときにも当てはまるもの。

- **フォークが `src/3rdparty/` に BSD などのライブラリを足したら、バイナリの配布物に
  そのライセンス文を入れる。** upstream の `packagezip.py` は入れない
- **再配布の根拠が確かめられないデータは、zip に入っていないことを SHA1 で検査する**
